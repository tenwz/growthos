# Contributing to growthOS

The highest-value contribution is not a feature. It is a **real repo using growthOS** and a **failing case the validator misses**.

## Setup

```bash
git clone https://github.com/tenwz/growthos.git
cd growthos
pnpm install
pnpm demo
pnpm test
```

Requirements: Node 20+, pnpm 10+.

## Project layout

```text
packages/core     # schemas, loader, evidence engine, score, cockpit, providers
packages/cli      # the published `growthos` binary
packages/mcp      # local stdio MCP server
templates/base    # scaffold for new repos
examples/hvac-saas# synthetic demo, generated by scripts/generate-demo.ts
skills/           # Agent Skills
spec/             # Growth Repo Spec + generated JSON Schemas
growth/           # this repo's own dogfood Growth OS
```

## The rules we will not trade

1. **Determinism.** `doctor`, `score`, and `demo` must not call an LLM.
2. **No network in the core path.** `demo` and `doctor` run offline.
3. **No scraping, auto-DM, or auto-send.** Any PR that adds these is closed.
4. **Every new evidence rule needs a fixture** that fails without it and passes with it.
5. **Published memos are immutable.** Tooling must refuse to overwrite them.
6. **Signal text is untrusted.** Never interpolate it as instructions or shell commands.
7. **No secrets in the repo.** CI scans for common key patterns.

## Development commands

```bash
pnpm build            # bundle the CLI with tsup
pnpm typecheck        # tsc --noEmit
pnpm test             # vitest
pnpm lint             # biome
pnpm schemas          # regenerate spec/schemas
pnpm validate:fixtures# validate examples/hvac-saas
pnpm pack:smoke       # pack + install + run demo
pnpm demo             # run the demo from source
```

## Adding an evidence rule

1. Write a failing fixture in `packages/core/test/`.
2. Add a `CheckResult` in `packages/core/src/evidence/check.ts` with a stable `rule` ID.
3. Decide its severity for drafts vs published memos.
4. Update `docs/scoring.md` only if it affects points.
5. Update the spec's rule table in `spec/growth-repo-spec-v0.1.md`.
6. Run `pnpm test` and `pnpm validate:fixtures`.

Rule IDs are public API. Do not rename one without a migration note.

## Adding a CLI command

- Put it in `packages/cli/src/commands/`.
- Use `requireRepo()` / `--root` consistently.
- Support `--json` if the output is data.
- Use the exit codes in `ui/exit-codes.ts`.
- Add an E2E test that spawns the CLI.

## Adding a provider

- Implement the `Provider` interface in `packages/core/src/providers/`.
- Do not read API keys yourself; use the configured environment variable.
- Never send signal text anywhere except the configured model endpoint.
- Add a test with a stub server or stub command.

## Editing the demo

`examples/hvac-saas` is generated. Edit `scripts/generate-demo.ts`, then:

```bash
pnpm tsx scripts/generate-demo.ts
pnpm test
pnpm validate:fixtures
```

The demo output is an acceptance test. If you change the numbers, update the README, tests, and score expectations together.

## Commit style

Conventional commits are appreciated:

```text
feat(cli): add score --badge
fix(core): reject citations to superseded signals
docs: explain the receipt hash
test: cover duplicate claim detection
```

## Pull requests

Before opening:

- [ ] `pnpm lint`
- [ ] `pnpm typecheck`
- [ ] `pnpm test`
- [ ] `pnpm validate:fixtures`
- [ ] `pnpm schemas:check`
- [ ] README or docs updated for user-facing changes
- [ ] No generated `packages/cli/assets/` or `*.tgz` committed

In the description, include:

- the behavior before and after;
- a real example (repo, command, output);
- what would make this change wrong.

## Translations

Chinese docs live in `docs/zh/` and `README.zh-CN.md`. Keep commands and numbers identical. Natural Chinese is better than literal translation. Do not translate rule IDs or field names.
